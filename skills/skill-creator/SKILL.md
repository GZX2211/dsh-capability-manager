# 技能创建助手

把要长期复用的方法、知识或工作流沉淀为可安装的技能。技能写给另一个 Agent 实例执行：只保留它需要且不易自行推断的信息，省略常识与动机性说明。

## 路径

```
{{STATE_DIR}}/skills/<name>/
├── SKILL.md（必需）
├── scripts/          - 可执行代码（Python/Bash 等）
├── references/
└── assets/
```

## 设计原则：渐进式披露

内容按三级加载分配：

1. name + description：常驻技能目录，约 100 词内，决定技能何时被触发。
2. SKILL.md 正文：触发时加载，控制在 5k 词内，只放核心工作流。
3. scripts/、references/、assets/：按需读取或执行，容量不限（脚本可不读入上下文直接运行）。

## 创建流程

按顺序执行，仅在明确不适用时跳过或询问：

1. **理解用途**：从当前对话提炼技能目标、典型触发语句、可复用方法和硬约束。信息不足时，向用户索取 1–2 个具体使用示例（用户会说什么、期望得到什么），一次只问最关键的问题。推荐能力级粒度，不把一次性任务原样封装成技能。
2. **确认方向**：用自然中文向用户复述理解和建议方案，等待明确确认后再动手。
3. **规划文件**：默认只创建 SKILL.md，逐项判断是否增加资源：
   - 反复重写或要求确定性可靠的操作 → scripts/
   - 执行时需查阅的详细资料（模式、API 文档、领域知识）→ references/
   - 输出中要复用的模板、素材、示例文件 → assets/
   - 缺少用户提供的资料（品牌模板、内部文档等）时先索取。4. **编写**：
   - 先用 `meta_search` 的 `names` 通道确认名称未被占用
   - 每条内容写入前做迁移测试：换一个项目这条还成立吗？仅当前项目成立的限制是项目事实，不写入技能。
   - 然后按下方兼容规范写 SKILL.md 和资源。正文用祈使句，不用第二人称；引用每个资源时写清何时读取或运行。
5. **验证与迭代**：新增脚本必须实际运行代表性用例并修复失败后再交付。技能投入使用后，根据真实任务中暴露的困难或低效之处更新 SKILL.md 或资源，并再次验证。
6. 完成后告知用户技能已生效；新建能力默认在「能力池」内、默认不常驻；如需调整，请点击左上角「能力管理」。

## 需要脚本时

`scripts/` 下的可执行代码统一用 Python（≥ 3.11），不写 shell 脚本；技能不需要脚本时跳过本节。

动笔前先读 `references/script-execution.md`：内含调用样板与四条硬约束（同目录导入、`sys.argv`、单 cell 120 秒、64KB 输出）。脚本由会话内的 `run_python` 执行，跑在 DSH 自带解释器上，与用户终端的 `python` 无关。

交付前用无副作用参数真实跑一次，按报错回改脚本而不是只改文档。

## 兼容规范

### 目录与文件

- 技能目录名与 name 一致；SKILL.md 位于目录根部，必须是普通文件，不能是目录、符号链接或嵌套在子目录中。
- SKILL.md 以合法且闭合的 YAML frontmatter 开头，正文放在第二个 --- 之后。

### Frontmatter

- name、description 必填，均为非空单行标量。name 用简短、语义清晰的 kebab-case；禁止块标量（|、>、|-、>- 等）、换行、/ 和反斜杠，不能为 . 或 ..。
- description 写清"做什么 + 何时触发"，覆盖用户可能的触发说法；用单行普通字符串或引号字符串，避免不必要的 YAML 转义。
- 可选字段只使用当前 loader 支持的字段和取值（如 allowed-tools、metadata），没有实际用途就省略。

### 正文与资源

- 核心工作流留在 SKILL.md；同一信息只出现一处，详细示例、模式和参考材料移入 references/，避免重复内容和深层引用链。
- references/ 单文件超过 10k 词时，在 SKILL.md 中给出检索关键词或使用 grep 模式。
- assets/ 中的文件用于产出，不读入上下文。
