## 1. 产品定义

### 1.1 一句话

一个独立安装的全局插件，把「模型初始能看到的所有工具与 Skill」压缩到最小，其余能力通过一个 `meta_search` 工具按需召回；同时给用户一个界面来决定哪些能力可用、哪些常驻，以及在 Personal Agent 存在时按 Router / Worker 角色差异化管理。

### 1.2 能力模型

```
能力 = 工具 + Skill
工具 = 官方工具 + 自建工具 + MCP 工具
Skill = 官方 Skill + 自建 Skill
```

### 1.3 每个能力只有两个用户可配状态

| 状态 | 含义 | 影响 |
|---|---|---|
| **池内 / 池外** | 是否允许被使用 | 池外：不可调用、不可召回、不注入上下文 |
| **常驻 / 非常驻** | 启动时是否直接可用 | 非常驻：启动不可见，须经 `meta_search` 召回 |

常驻是池的子集（池外的能力不能常驻）。

### 1.4 判定顺序（权威，任何实现不得偏离）

对任意一次「能力 X 是否对 Agent A 可用」：

```
第 1 步  角色黑名单
         A 的角色 ∈ {router, worker} 且 X 在该角色黑名单 → 不可用、不可召回、不注入，结束
         否则 → 进入第 2 步

第 2 步  能力池
         X ∉ 池 → 不可用、不可召回、不注入，结束
         X ∈ 池 → 进入第 3 步

第 3 步  常驻判定
         X ∈ 常驻 → 启动即直接可用
         X ∉ 常驻 → 启动不可见，只能经召回进入

第 4 步  召回判定
         召回范围 = 池 − 该角色黑名单
         返回前执行载荷级去重

第 5 步  使用判定
         工具：常驻的直接调；召回的凭返回的完整 schema 调
         Skill：常驻的直接调 skill 工具加载；召回的凭返回的索引条目再调 skill 工具
```

**优先级：黑名单 > 池 > 常驻。** 黑名单可以排除池内能力，也可以排掉常驻能力。

### 1.5 可见集公式（实现直接照抄）

```
Agent A 在第 N 步可见的工具集合 =
  (  常驻工具
   ∪ 本会话历史召回的工具
   )
  ∩ 池内工具
  − A 的角色黑名单
```

「本会话历史召回」由 `Session.toolHistory()` 重建——**重启后必须仍然有效**，不需要重新召回。

### 1.6 默认形态（开箱状态）

```
池   = 全部工具 + 全部 Skill（含 meta_search 与 skill 自己）
常驻 = { tool:meta_search, tool:skill }
黑名单 = 空
向量检索 = 关闭
```

理由：`meta_search` 是检索入口，`skill` 是加载 Skill 正文的入口，两者互为「元能力」。少任何一个都会让「召回 → 使用」多一次往返或直接断链。

**注意**：`meta_search` 与 `skill` 都是**普通池内能力**——可以被用户排除出池、也可以被取消常驻。这不违反任何契约，只是需要界面给出风险提示（§3.5）。

## 2. 运行环境事实（已验证，实现必须按此假设）

### 2.1 Scope 层级与工具可见性

Cordis 的 scope 链（nearest-first）：

```
agent scope              ← createScope(loopCtx, agent)；agent.ctx 注册的东西在这层
  ↑ parent
preset generation scope  ← 标准 preset 挂的工具在这层（bash/pwsh/fs/… 共约 41 个）
  ↑ parent
root / global            ← dsh-base 的全局工具、以及本插件注册的工具
```

### 2.2 `ctx.tools.restrict` 的精确语义

```ts
restrict(filter: { allow?: string[]; deny?: string[] }): () => void
```

- **必须在 `agent.ctx` 上调用**；在无 scope 的 ctx 上调用会抛 `tools.restrict() requires a scoped context`。
- `allow` = 只留这些；`deny` = 去掉这些；两者可同时给，多条 restriction **取交集**。
- 作用范围：**global 层 + 所有祖先 scope 层**。
- **不作用**：当前 scope 自己（agent 层）注册的工具——那一层无条件可见。
- 名单里出现**未知工具名会抛错**；调用前必须与当前已注册工具名取交集。
- 返回 disposer；调用后 restriction 解除。
- 变更会同步发出 `tools/change` 事件。

### 2.3 工具集变化的原生增量协议

`dsh-agent-loop` 每次请求前对比 `request/header.tools` 与当前工具集，追加 `developer/message`，内容为 `tool-addition` / `tool-removal` 块。

本机 profile 已配置：

```
toolUpdate: addition-only
systemPromptUpdate: in-history
```

因此：

- **新增工具不会破坏 KV 前缀缓存**；
- **移除工具不会发出移除通知**——模型可能仍以为旧工具可用，调用时报 `UNKNOWN_TOOL`。

### 2.4 Skill 目录的官方行为（必须 shadow 的理由）

`@deepseek-ai/dsh-tool-skill` 的行为：

- 只要 `skill` 工具可见，就在**第一个请求前**注入一份 `<available_skills>` 目录（每个 model-invocable skill 的 `name` + 截断描述）；
- 目录内容 = **全部** model-invocable skill，**没有任何过滤钩子**；
- 只有在「`skill` 工具被隐藏」或「被同名工具 shadow」时才不注入。

`@deepseek-ai/dsh-skill` 的判定规则：

- `modelInvocable: true` 的 skill 一定进目录，且能被 `skill` 工具加载；
- `modelInvocable: false` 的 skill 不进目录，**官方 `skill` 工具也拒绝加载**。

→ 结论：要做到「Skill 也受能力池管辖」，**必须**在 agent scope 注册一个同名 `skill` 工具把官方的 shadow 掉，并由我们自己注入目录。

可复用的官方导出（从 `@deepseek-ai/dsh-skill`）：

```ts
renderSkillContent(...)      // 渲染 <skill_content> 块，加载与手势共用
isModelInvocable(skill)      // 过滤
isUserInvocable(skill)
```

### 2.5 会话载荷的权威读取点

| 载荷 | 读取点 |
|---|---|
| 工具的完整 schema（已在本会话出现过） | `Session.toolHistory()` → `{ tools, updates }`；`updates[].additions` 是历史新增 |
| 最近一次请求的活跃工具集 | `Session.requestHeader()?.tools` |
| Skill 索引 | 我们自己注入的目录消息（session 日志中的 user message） |

### 2.6 角色查询

Personal Agent 暴露只读服务：

```ts
ctx.paRoles.roleOf(sessionId: string): 'router' | 'worker' | undefined
```

- 服务未注册（PA 未安装）时 `ctx.get('paRoles')` 返回 `undefined`；
- 服务已注册但账本未就绪时 `roleOf` 返回 `undefined`；
- **`undefined` 一律按「未知角色」处理**：不应用任何角色黑名单。

### 2.7 事故教训（写进代码规范）

**`agent/pre-step` 是 waterfall 事件。** 签名：

```ts
'agent/pre-step'(payload: { agent; messages; turn; step; signal; modelSelection }, next: () => Promise<PreStepDecision>): Promise<PreStepDecision>
```

`PreStepDecision` 必须是 `{ kind: 'reject' }` 或 `{ kind: 'enter', messages, startsRequestSeries? }`。
用 `ctx.on` 注册并返回 `undefined` 会让 agent-loop 读 `decision.kind` 时崩溃整个 Host。

**规则：waterfall 事件一律用 `ctx.waterfall(...)` 注册，并且必须返回 `next()` 的结果。** 普通 `ctx.on` 只用于 event 模式的事件（`agent/created`、`agent/disposed`、`tools/change` 等）。

`@deepseek-ai/dsh-client-ui-primitives` 是宿主 boot 提供的 seed 模块，插件可直接 `import`。本方案用到：

`dsh-client-ui-sidebar/README.md:42`：

## 3. 行为契约（验收依据）

### 3.1 能力池

- CP-1 所有能力默认在池内。
- CP-2 用户可在界面把能力排除出池。
- CP-3 池外能力：不可调用、不可召回、不注入上下文。
- CP-4 池的范围同时决定：`meta_search` 召回范围、索引条目范围、常驻配置候选范围。
- CP-5 `meta_search` 与 `skill` 本身也在池内，可被排除。
- CP-6 池是全局的，不区分角色。

### 3.2 常驻（原「初始配置」）

- IC-1 常驻只能从池内选。
- IC-2 常驻包含工具与 Skill。
- IC-3 常驻工具启动后无需召回即可调用。
- IC-4 常驻 Skill 启动后无需召回即可加载。
- IC-5 `meta_search` 可常驻也可不常驻，不是固定项。
- IC-6 常驻可以是「只有 `meta_search` + `skill`」「加上其他能力」「一个都没有」。
- IC-7 黑名单优先于常驻：常驻能力被某角色黑名单排除后，对该角色仍不可用。

### 3.3 `meta_search`

**召回通道**

| 通道 | 触发 | 依赖 embedding | 受向量开关影响 |
|---|---|---|---|
| 语义召回 | `keywords` 参数 | 是 | 是，仅开启时生效 |
| 正则精确召回 | `names` 参数 | 否 | **否，永远生效** |

**返回内容**

| 对象 | 返回 |
|---|---|
| 工具 | 完整 schema（`name` + `description` + `parameters`），使模型可直接调用 |
| Skill | 索引条目（`name` + `description`），不含正文；正文由 `skill` 工具加载 |

**召回范围**：`池 − 该角色黑名单`。

**去重（载荷级）**

- 比较对象：本次召回载荷 vs 本会话已出现过的**同类型**载荷。
- 判定标准：**逐字完全一致**才剔除；不做名称级、语义级、字段级模糊判重。
- 载荷类型：工具载荷 = 完整 schema 的规范化 JSON；Skill 载荷 = `name` + `description` 条目。
- 工具索引 ≠ 工具 schema，不互相判重；Skill 索引 ≠ Skill 正文，不互相判重。
- 被剔除项不出现在返回值里。

### 3.4 两种运行模式

| | 模式 A（向量检索关闭，默认） | 模式 B（向量检索开启） |
|---|---|---|
| 语义召回 | 不生效 | 生效 |
| 正则召回 | 生效 | 生效 |
| 索引注入 | 注入：非常驻工具的索引 + **全部**池内 Skill 的索引 | 不注入 |
| 工具召回 | 返回完整 schema | 返回完整 schema |
| Skill 召回 | 恒返回空（索引已全量常驻，被去重剔除），返回 notes 说明原因 | 返回索引条目 |
| 非常驻 Skill 使用 | 凭常驻索引直接调 `skill` 工具 | 先召回索引再调 `skill` |

**索引注入的前置条件**：模式 A 且 `meta_search` 在常驻中。若 `meta_search` 非常驻，注入索引只占上下文却不产生召回能力，因此不注入。

### 3.5 风险提示（界面必须显示）

| 场景 | 提示 |
|---|---|
| `meta_search` 不在常驻，但池内存在非常驻能力 | 这些能力将无法被召回使用 |
| `meta_search` 被排除出池 | 完全无法召回，Agent 只能靠常驻能力工作 |
| `skill` 被排除出池 | 所有 Skill 都不可加载 |
| 常驻为空 | Agent 启动时无任何直接可用能力 |
| 黑名单排除了常驻能力 | 该能力对该角色将不可用 |
| 模式 A 且 `meta_search` 非常驻 | 索引不注入以省上下文 |

### 3.6 角色黑名单

- BL-1 黑名单对象是能力（工具 + Skill）。
- BL-2 黑名单优先级最高，可排除池内与常驻能力。
- BL-3 对另一角色和全局无影响。
- BL-4 配置存在本插件。
- BL-5 MCP 连接是全局的，黑名单不影响连接，只影响该服务器下的工具是否分配给该角色。
- BL-6 角色判定：先问 `ctx.paRoles`，未知则按「无角色」处理（不应用任何黑名单）。
- BL-7 **仅在检测到 `paRoles` 服务时，界面才出现 Router / Worker 两个配置窗口。**

### 3.7 MCP

- 连接是全局的；本插件不新建连接编辑器。
- 界面只读展示 `ctx.mcpManager.list()` 的结果，并提供「池内/池外」控制。
- 新建/修改 MCP 由内置 `capability-creator` Skill 指导用户与 Agent 完成。

### 3.8 创建能力

- 工具创建、Skill 创建、MCP 创建**全部由内置 Skill 承担**，插件不提供专用创建工具或表单。
- 插件只提供**注册与热生效**机制：
  - 自建工具：写入状态目录 → 插件监听并注册到 global 层。
  - 自建 Skill：写入状态目录 → 插件 provider 发现并在目录中呈现。
- 新建能力默认进池、默认**不**常驻。

### 3.9 热生效

- 自建工具/Skill 注册后 `tools/change` / skills 变化 → 所有活跃 agent 的白名单立即重建 → 下一个 step 生效。
- 已运行会话受 `addition-only` 约束：新增可见，移除不可见（§2.3）。界面需提示「收紧配置对进行中会话有延迟，必要时新建会话」。

### 3.10 边界场景

| 场景 | 行为 |
|---|---|
| 池为空 | Agent 无任何能力；界面提示 |
| 常驻为空 | Agent 启动时无直接可用能力；界面提示 |
| `meta_search` 池内但非常驻 | 启动不可用，无法召回；界面提示 |
| 向量检索开启但模型下载失败 | 保持关闭，提示失败原因；正则召回不受影响 |
| MCP 服务器连接失败 | 该服务器下工具不可用，不影响其他能力 |
| 自建工具名与已有冲突 | 创建时校验并拒绝注册，记录日志；不覆盖已有工具 |

## 4. 数据契约（`src/shared/`）

### 4.1 能力标识

```ts
export type CapabilityKind = 'tool' | 'skill'

/** tool:<name> | skill:<name>；Skills 名与工具名不共享命名空间。 */
export type CapabilityId = string

export function toolId(name: string): CapabilityId   // `tool:${name}`
export function skillId(name: string): CapabilityId  // `skill:${name}`
export function parseId(id: CapabilityId): { kind: CapabilityKind; name: string } | undefined
```

### 4.2 能力条目

```ts
export type CapabilitySource = 'official' | 'custom' | 'mcp'

export interface CapabilityEntry {
  id: CapabilityId
  kind: CapabilityKind
  name: string
  /** 单行摘要，工具取 description 首行并截断到 200 字符；Skill 取 catalog 描述 */
  summary: string
  source: CapabilitySource
  /** 该来源是否由本插件自建（决定能否删除/编辑） */
  owned: boolean
  /** 当前是否可被模型调用（工具在 agent 视角可见 / skill 可加载） */
  available: boolean
}
```

来源判定：

- `official`：不是本插件注册的、且不在自建目录里；
- `custom`：来自 `<state>/tools/` 或 `<state>/skills/`；
- `mcp`：工具名属于 `ctx.mcpManager.list()` 中某个服务器的命名空间（工具名形如 `<server>__<tool>`，实现时按官方 mcp-client 的命名规则判断）。

### 4.3 配置

位置：`<DSH_HOME>/state/capability-manager/config.json`（原子写：写临时文件 + rename）。

```ts
export interface CapabilityConfig {
  version: 1
  /** 排除出能力池的能力 id */
  excluded: CapabilityId[]
  /** 常驻能力 id（必须同时在池内，读取时要自愈：剔除池外的项） */
  resident: CapabilityId[]
  /** 角色黑名单 */
  blacklist: { router: CapabilityId[]; worker: CapabilityId[] }
  /** 向量检索 */
  embedding: {
    enabled: boolean
    /** 已下载的模型目录（相对 state 目录），未下载为 undefined */
    modelDir?: string
    /** 模型 revision，用于升级判断 */
    revision?: string
  }
  /** 手动角色绑定覆盖，sessionId → 角色 */
  roleBindings: Record<string, 'router' | 'worker'>
}

export const DEFAULT_CONFIG: CapabilityConfig = {
  version: 1,
  excluded: [],
  resident: [toolId('meta_search'), toolId('skill')],
  blacklist: { router: [], worker: [] },
  embedding: { enabled: false },
  roleBindings: {},
}
```

读取时的自愈规则（必须实现，否则配置漂移会让 `restrict` 抛错）：

1. `resident` 中不在池内的项被丢弃（并记日志）；
2. 所有 id 若解析出的 kind/name 不合法则丢弃；
3. `excluded` 中不存在的工具名不丢弃（工具可能只是当前未加载），但在生成 `restrict` 名单时按 §5.4 过滤。

### 4.4 HTTP 端点

前缀 `/capability-manager/api`，同源；与 PA 一致带自定义头 `x-capability-manager-request: 1` 与 origin 校验。

| 方法 | 路径 | 请求 | 响应 |
|---|---|---|---|
| GET | `/snapshot` | — | `SnapshotResponse` |
| POST | `/config` | `ConfigPatch` | `{ ok: true; revision: number }` |
| POST | `/embedding/enable` | — | `{ ok: true }` 或 `{ ok: false; code; message }` |
| POST | `/embedding/disable` | — | `{ ok: true }` |
| GET | `/health` | — | `{ ok: true; version; stateDir }` |

```ts
export interface SnapshotResponse {
  revision: number
  capabilities: CapabilityEntry[]
  config: CapabilityConfig
  /** 已检测到 paRoles 服务时为 true，界面据此显示黑名单窗口 */
  rolesAvailable: boolean
  embedding: {
    enabled: boolean
    /** idle | downloading | verifying | ready | failed */
    status: 'idle' | 'downloading' | 'verifying' | 'ready' | 'failed'
    progress?: { received: number; total?: number }
    message?: string
  }
  warnings: Array<{ code: WarningCode; capabilityIds?: CapabilityId[] }>
}
```

## 5. `meta_search` 的完整规格

### 5.1 工具 schema

```ts
name: 'meta_search'
description: `召回当前会话可用的工具与 Skill。

何时调用：你不确定有哪些工具或 Skill 可用时；或已知能力名但当前看不到它的完整定义时。

参数：
- names：准确名称或名称组（支持正则片段，如 "read|write|edit"），按名称精确匹配，永远可用，支持批量。
- keywords：自然语言关键词，按语义相似度召回，仅在开启向量检索时生效。

返回：tools 为可直接调用的完整 schema；skills 为索引条目（name + description），
正文需再调用 skill 工具加载。返回为空表示这些能力已在当前上下文中，或不在能力池内。

失败：正则非法时返回错误并保留其余结果；向量检索未开启时 keywords 通道被忽略并在 notes 中说明。`

parameters: {
  names?: { type: 'string', description: '名称组，支持 | 分隔的正则片段' },
  keywords?: { type: 'string', description: '自然语言关键词' },
  limit?: { type: 'number', description: '最多返回条数，默认 20，上限 50' },
}
```

### 5.2 返回结构

```ts
output: {
  schema: {
    type: 'object',
    properties: {
      tools: { type: 'array', items: { type: 'object' } },   // { name, description, parameters }
      skills: { type: 'array', items: { type: 'object' } },  // { name, description }
      notes: { type: 'array', items: { type: 'string' } },
    },
  },
}
```

`render`：渲染成模型可读文本，工具段用 `### <name>` + description + JSON schema；Skill 段用列表。

### 5.3 执行流程

```
1. 取 agent（exec.agent）与 session；无 agent 时返回错误（本工具只在会话内可用）
2. 读取配置与能力目录
3. candidates = catalog ∩ 池 − 该角色黑名单
4. names 通道：对 candidates 的 name 做正则匹配（大小写不敏感，未锚定，用户给的串直接作为片段）
   - 正则非法 → 记录 note，跳过该通道
5. keywords 通道：仅当 embedding.enabled 且模型 ready
   - 对 candidates 的 summary 做向量检索，取 top-K（默认 10，阈值 0.35）
   - 未开启 → 记录 note「向量检索未开启，已忽略 keywords」
6. 合并去重（按 capability id），保持 names 命中优先
7. 构造载荷：
   - 工具：完整 schema（与 `ctx.tools.schemas(agent)` 中同名项一致）
   - Skill：`{ name, description }`（与我们注入的目录条目逐字一致）
8. 载荷级去重：与 session 已出现载荷比较（§7.4 的实现），剔除逐字一致项
9. 对本次返回的工具，把名字记入该会话的召回集合，触发白名单重建（§6.5）
10. 返回 { tools, skills, notes }
```

### 5.4 载荷规范化（去重的比较基准）

```ts
/** 工具载荷：稳定序列化，键序固定。 */
function toolPayload(schema: ToolSchema): string {
  return JSON.stringify({
    name: schema.name,
    description: schema.description ?? '',
    parameters: canonicalize(schema.parameters),
  })
}

/** Skill 载荷：与目录里那一行逐字一致。 */
function skillPayload(entry: { name: string; description: string }): string {
  return `${entry.name}\u0000${entry.description}`
}
```

`canonicalize` 对 JSON 对象递归排序键，保证同一 schema 一定产出同一字符串。**不做任何截断或省略**——去重判定是逐字一致，任何规范化放宽都会破坏契约。

### 5.5 向量检索子系统

**模型**：`Xenova/bge-small-zh-v1.5`

| 文件 | 大小 | 说明 |
|---|---|---|
| `onnx/model_quantized.onnx` | 24 MB | int8 量化，唯一需要下载的权重 |
| `tokenizer.json` | 439 KB | |
| `config.json` | 716 B | |

**下载源**（依次探测，首个 2xx 优先）：

```
https://huggingface.co/<repo>/resolve/<revision>/<path>
https://hf-mirror.com/<repo>/resolve/<revision>/<path>
```

固定 revision（写入代码常量），下载后校验 sha256 与 size，不匹配则删除重下。

**存储**：`<state>/models/bge-small-zh-v1.5/{model_quantized.onnx,tokenizer.json,config.json,manifest.json}`

**推选型**：实现时按下列顺序尝试，取第一个在 Electron 主进程可用的：

1. `onnxruntime-node`（CPU，性能最好）
2. `onnxruntime-web`（WASM，无原生依赖）

选定后写进 `package.json` 依赖，并记录实测结论。

**Tokenizer**：自实现 BERT WordPiece，输入 `tokenizer.json` 的 `model.vocab`：

```
basicTokenize: 中文按字切；拉丁按词 + 标点切；转小写；去重音
wordPiece: 贪心最长匹配，前缀 ## 表示词内
特殊 token: [CLS] id=101, [SEP] id=102, [PAD] id=0
序列: [CLS] tokens [SEP]，截断到 512
```

池化：取 `last_hidden_state` 的 `[CLS]` 位置（BGE 用 CLS 池化），再 L2 归一化。

**缓存**：`<state>/models/bge-small-zh-v1.5/vectors.json`

```json
{ "<capabilityId>": { "hash": "<sha256 of summary>", "vector": [0.01, ...] } }
```

条目 summary 变化时才重算。启动时惰性加载，不进热路径。

**检索**：余弦相似度（向量已归一化，直接点积），取 top-K。

### 6.3 每 agent 的应用逻辑（核心）

**先解决一个陷阱：不能用 `ctx.tools.definitions(agent)` 当「工具全集」。**

`definitions(scope)` 返回的是**已经应用过 restriction 的可见集**。一旦上一步把非常驻工具掩掉，下一步就再也读不到它们，`allow` 只会越算越小，被掩掉的工具永远回不来。

因此必须维护一个**不受 restriction 影响的已知全集**。

#### 6.3.1 `knownUniverse` 的维护规则

```ts
/** 插件级：本部署中出现过的全部工具名，是计算 allow 的唯一依据。 */
const knownUniverse = new Set<string>()
```

| 时机 | 动作 | 为什么可靠 |
|---|---|---|
| `agent/created`，**应用 restriction 之前** | `for (const d of ctx.tools.definitions(agent)) knownUniverse.add(d.name)` | agent 创建时 preset 组合已完成，这一刻读到的是完整全集，且尚未被我们限制 |
| 本插件注册任何工具时 | 主动 `knownUniverse.add(name)` | 注册方自己知道名字 |
| `tools/change` | 走「临时解除 → 重读 → 恢复」补齐（见下） | 覆盖 MCP 连接、官方动态注册等外部增量 |

补齐实现（仅在 `tools/change` 且距上次补齐超过 200ms 时执行，避免抖动）：

```ts
function refreshUniverse(agent: Agent): void {
  const binding = bindings.get(agent.id)
  binding?.disposeRestrict?.()               // 临时解除
  try {
    for (const d of ctx.tools.definitions(agent)) knownUniverse.add(d.name)
  } finally {
    binding?.applyRestrict?.()               // 立刻恢复
  }
}
```

这个窗口是同步的（同一事件循环内解除并恢复），不会让模型看到中间状态。

#### 6.3.2 应用逻辑

```ts
interface AgentBinding {
  agentId: SessionId
  /** 上一次生成的 allow 名单，用于短路（内容不变就不重建） */
  allowKey: string
  /** 上一次成功应用的 restriction；allow 为空时保留它 */
  applied: string[]
  disposeRestrict?: () => void
  disposeShadowTool?: () => void
  disposeCatalogListener?: () => void
}

function applyToAgent(agent: Agent): void {
  const recalled = recalledStore.namesOf(agent.session)   // 从 toolHistory 重建
  const allow = computeAllow({
    config,
    role: roleOf(agent.session.id),
    universe: knownUniverse,
    recalled,
  })
  if (allow.length === 0) {
    // 空 allow 会隐藏一切工具。绝不因为一次异常计算让 Agent 全盲。
    logWarning(`allow 为空，保留上一次限制（${binding.applied.length} 项）`)
    return
  }
  const key = allow.join('\u0000')
  if (binding.allowKey === key) return
  binding.disposeRestrict?.()
  binding.disposeRestrict = agent.ctx.tools.restrict({ allow })
  binding.allowKey = key
  binding.applied = allow
}
```

`computeAllow`（纯函数，必须单测）：

**先补一个 `present` 集合**（每个 agent 一份，见 D-2）。`universe` 是「曾出现过」的并集、只增不减，必然包含已经消失的名字（MCP 断开、插件卸载、preset 切换）；而 `restrict` 命中未知名字会抛错。所以还要有「当前确实存在」的集合：

| 时机 | 取值 |
|---|---|
| `agent/created`，应用 restriction 之前 | 直接读 `ctx.tools.definitions(agent)` |
| `tools/change` | 临时解除自己的 restriction → 读 → 立即恢复（同一事件循环内） |

```
computeAllow({ config, role, universe, present, recalled }) =
  排序去重(
    ( universe
      ∩ present
      ∩ ( 常驻工具名 ∪ recalled )
      ∩ ( universe − 池外工具名 )
    )
    − 该角色黑名单工具名
  )
```

**注意**：Skill 不是工具，不进 `allow`；Skill 的可见性由目录注入与 `skill` 工具的加载校验控制。

### 6.4 shadow `skill` 工具

在 `agent/created` 时通过 `agent.ctx` 注册：

```ts
agent.ctx.tools.register({
  name: 'skill',
  description: '按名称加载一个 Skill 的完整指令。...',
  parameters: { name: { type: 'string', required: true } },
  output: { schema: {...}, render: ... },
  when: () => isInPool(skillToolId) && !isBlacklisted(role, skillToolId),
  async execute(args, exec) {
    const skill = await ctx.skills.get(args.name, { cwd, signal: exec.signal, scope: exec.agent })
    if (skill === undefined) throw new Error(`skill "${args.name}" is unknown or no longer available`)
    if (!isInPool(skillId(skill.name)) || isBlacklisted(role, skillId(skill.name))) {
      throw new Error(`skill "${skill.name}" is not available in this session`)
    }
    return renderSkillContent(skill, ...)
  },
})
```

**为什么要 `when`**：agent 层注册的工具不受 `restrict` 约束（§2.2），只有 `when` 能控制它是否出现在 executor description 里。

**为什么官方目录不会重复注入**：官方 consumer 检查「`skill` 工具当前可见的定义是否还是它自己注册的那个」。我们注册的是同名定义，它比较后判定被 shadow，就不再注入目录（§2.4）。

### 6.5 召回后重建

`meta_search` 执行末尾：

```ts
recalledStore.add(session, toolNames)   // 内存 + 依赖 toolHistory 兜底
enforcement.applyToAgent(agent)          // 立即重建 restriction
```

下一 step 的 `resolve()` 会重新读 view，新工具出现，agent-loop 自动追加 `tool-addition`。

**同一 step 内连续两次 `meta_search` 不会互相看到对方的召回结果**——因为 restriction 重建后要等下一次 step 才生效。因此 `meta_search` 的返回值必须自带完整 schema（§5.2 已如此定义），同一 step 内模型可以照返回的 schema 直接写调用参数，但**执行会失败**。这属于已知限制，在工具 description 里写明「返回的能力从下一步开始可调用」。

### 6.6 索引注入（模式 A）

```ts
ctx.systemPrompt.section({
  name: 'capability-manager/index',
  order: 10150,                     // 放第一方环境后缀之后：静态 prompt 在前，动态索引在后

    if (agent === undefined) return ''

```

**注入范围（两侧不对称，这是刻意的）**

| 类型 | 列什么 | 为什么不列其他的 |
|---|---|---|
| 工具索引 | **池内 − 常驻 − 黑名单**（即只列非常驻的那些） | 常驻工具的完整 schema 已经在 API tools 里，再列一遍纯属重复占上下文 |
| Skill 索引 | **池内 − 黑名单**（全部，含常驻与非常驻） | Skill 没有别的可见通道。技能目录是模型唯一能知道「有这个名字」的地方，不给它，正则召回也无从下手 |

**必须过滤**：池外、该角色黑名单，以及本会话中已以完整 schema 出现过的工具。
**工具索引不是 schema**：只给名称和一行摘要，明确写出「要使用请调用 meta_search」。

**模式 A 下 `meta_search` 对 Skill 必然返回空，这是设计预期。** 因为 Skill 索引已经全量常驻，任何索引载荷都与上下文逐字一致，按载荷级去重规则会被全部剔除。此时返回值必须给出说明（§5.3 流程第 9 步的 notes），否则模型会反复重试：

```
notes: ['Skill 索引已在当前上下文中完整可见，无需召回；直接用 skill 工具按名称加载。']
```

渲染形状：

```markdown
<system-reminder>
以下清单只列出名称与用途摘要，不含调用参数。

<available_tools>
- `bash`：在 shell 中执行命令
- `read`：读取文本文件
</available_tools>
要使用上述工具，调用 meta_search。

<available_skills>
- `office-docx`：创建与编辑 Word 文档
</available_skills>

</system-reminder>
```

两个区块分别渲染：某一段为空时整段省略，两段都为空时 section 返回空串（不产生任何 token）。

## 附录 C　配置自愈与 `restrict` 的防错流程

每次生成 `allow` 前必须执行：

```
1. universe = knownUniverse（§6.3.1，绝不能用 definitions(agent)）
2. present  = 该 agent 当前确实存在的工具名（D-2）
3. desired  = 常驻工具名 ∪ 召回工具名
4. allow    = universe ∩ present ∩ desired ∩ (universe − 池外) − 黑名单
5. 若 allow 为空数组 → 不调用 restrict（空 allow 会隐藏一切，可能是配置错误的征兆）
   改为记录 warning 并保留上一次的 restriction（binding.applied）
6. 若 allow 与 binding.applied 相同 → 短路，不重建 restriction（避免无意义的 tools/change）
```

第 5 条是硬性要求：**绝不因为一次空计算结果就让 Agent 失去所有工具**。
第 6 条是性能要求：每次重建都会发 `tools/change`，无谓重建会拖慢每个 step。

### D-1　补充：前端控件包的类型来源（M1 发现，无需审批）

### D-2　待批变更：`computeAllow` 需要一个 `present` 入参（M1 发现）

涉及正文：§6.3.2 的 `computeAllow` 公式、附录 C 第 3 步。

**正文现状**

```
allow = universe ∩ desired ∩ (universe − 池外) − 黑名单
```

**问题**

`tools.restrict()` 在名单里出现**当前不存在的工具名**时会抛错：

```
tools.restrict() names unknown global tool "…"; known global tools: …
```

它的校验基准是 `view(scope).restrictableNames`——**pre-restriction** 的名字集合。
而 `knownUniverse` 是「曾经出现过」的并集，只增不减，因此**必然**会包含已经消失的名字
（MCP 服务器断开、插件卸载、preset 切换都会造成）。按正文公式算出的 `allow` 可能含有
这类名字，于是 `restrict` 抛错，中断整个 agent 创建。

**建议**

在公式里加入「当前确实存在」的集合 `present`（每个 agent 一份，来源见下），并取交集：

```
allow = universe ∩ present ∩ desired ∩ (universe − 池外) − 黑名单
```

`present` 的维护方式：

| 时机 | 动作 |
|---|---|
| `agent/created`，应用 restriction **之前** | 直接读 `ctx.tools.definitions(agent)` |
| `tools/change` | 临时解除自己的 restriction → 读 → 立即恢复，同一事件循环内完成 |

**为什么不能只靠 `universe`**：`definitions(agent)` 返回的是应用过 restriction 的可见集，
所以吸收全集时必须先解除自己的限制；而解除后读到的仍是「其他插件限制之后」的集合，
这一点无法消除，只能接受（记入风险）。

**影响范围**：只是把「可能抛错」变成「过滤掉不存在的项」，不放宽任何业务语义——
不存在的能力本来也不该出现在 `allow` 里。

### D-3　补充：装配末尾要为已存在的 agent 补一次（M1 实测发现，无需审批）

涉及正文：§6.2 装配顺序第 9 步。

**事实**：`agent/created` 只在 agent 被创建（含 resume）时触发。插件**热启用**或
Host 内重载时，profile 里已经活着的 agent 不会重新触发该事件，因此第 9 步的
`onAgentCreated` 对它们一次都不会执行。

**后果**：启用后当前会话完全不受管理——界面上显示「已启用」，实际工具一个没被收紧。
这比崩溃更难发现，因为一切看起来都正常。

**处理**：装配末尾遍历 `ctx.agents.list()` 对每个现存 agent 补一次
`enforcement.onAgentCreated`。`inject` 相应加上 `agents`。

**先例**：personal-agent 的 `decorateLiveWorkerSessions` 处理的正是同一件事
（重载后活着的 worker 不再发 `agent/created`）。

**影响范围**：只是补上遗漏的初始化，不改变任何可见行为；冷会话将来被唤醒时
仍会走正常的 `agent/created` 路径，重复调用是幂等的（binding 以 agent id 为键）。

**实现依据**：本记录只补齐正文没覆盖的一步，没有改动任何契约，故无需审批。

### D-4　补充：吸收只用 `definitions()`，且吸收失败不得收紧（M1 实测事故，无需审批）

涉及正文：§6.3.1 的「吸收」、§6.3.2 的 `applyToAgent`、附录 C。

**事故经过**（装进 profile 后立即发生）：

1. 限制成功应用，会话的工具被收到 `meta_search` + `skill`
2. 但 `meta_search` 每次召回都返回空——它拿到的候选集只有它自己
3. 于是会话被困住：工具都没了，召也召不回来
4. 关闭插件后限制仍未解除，只能重启

**根因一：`schemas()` 会抛错。**

§6.3.1 说的是「吸收工具全集」。实现里同时读了 `definitions()` 和 `schemas()`，而
`schemas()` 在真实 Host 上会抛错。两个调用放在同一个 `try` 里，于是：

- `definitions()` 先成功 → `present` 非空 → 限制照常应用
- `schemas()` 抛错 → 跳进 `catch` 提前返回 → **schema 缓存里只剩本插件自己登记的那一个**

**修正**：吸收只用 `definitions()`。`ToolDefinition` 本来就带 `name/description/parameters`，
`meta_search` 需要的三样它都有；`schemas()` 只是多一次投影，还多一个失败点。

**根因二：兜底释放器被反复重注册。**

为了让限制在插件卸载后也能解除，把 `restrict()` 的 disposer 同时挂到
`agent.ctx.effect` 上。但最初是**每次重建都注册一个新的**，并撤掉上一个——
撤掉一个 effect 会执行它的 cleanup，而那个 cleanup 里的 disposer 实现是
「删除本 agent 的限制」，**不幂等**：它删掉的是刚建立的新限制。

**修正**：兜底释放器在 `onAgentCreated` 里**只注册一次**，cleanup 内部读
`binding.release` 的当前值。这样重建不会碰它，agent 销毁时它释放的一定是当时有效的那个。

**根因三：缺熔断。**

吸收部分失败时仍然应用了限制。**修正**：`absorb()` 返回 `failed`，吸收失败时
完全不收紧、保持现状。

**流程教训（写进实现约束）**：

> 本插件的限制会收走使用者的工具，包括它自己。任何一步失败都必须朝「不生效」而不是
> 「生效一半」的方向降级；并且**绝不能出现「工具被收走、召回又不可用」的组合**——
> 那个组合会让会话失去自救能力。

由此确立两条硬约束：

1. 吸收失败、候选集为空、名单为空 → 一律不收紧
2. 限制的释放有两条独立路径：插件卸载时主动释放，agent 销毁时由宿主执行兜底释放器

**影响范围**：收紧的判定更保守（宁可少收），释放更可靠；不改变任何可见契约。

### D-5　变更：召回去重与索引排除的基准必须是「当前可见」而非「会话历史」（M1 事故根因）

涉及正文：§2.5「会话载荷的权威读取点」、§3.3 去重、§6.6 索引注入的「必须过滤」。

**正文说的**：工具的完整 schema「已在本会话出现过」读 `Session.toolHistory()`。

**实际造成的后果**：去重与索引排除都用了这个「历史全集」。而限制一旦生效，工具的
定义仍然留在历史里——于是每次召回的候选都被判成「已经在当前上下文中」而被全部剔除，
索引也永远不列它们。模型既看不到工具，也召不回来。

**这是那个「会话被锁死」事故的真正根因**（D-4 里记的 `schemas()` 抛错只是一个
更早暴露的、让候选集本身为空的独立缺陷）。

**修正**：两处的基准都改成该 agent **此刻可见**的工具集
（`agent.ctx.tools.definitions(agent)`）。

- 召回去重：当前可见的工具才算「已经在上下文里」，不该重复返回
- 索引排除：当前可见的工具已有完整 schema，不该再列进索引

**为什么历史全集是错的**：history 是「曾经出现过」，可见集是「现在还在」。
只有后者能回答「模型现在看不看得懂这个调用」。用前者等于假设工具永远不会被收走，
而这恰好是本插件存在的全部理由。

**影响范围**：能力被收走后仍能出现在索引里、并能被召回——正是本插件的核心行为。
去重的语义没有变（仍是逐字一致的载荷比较），变的是「与什么集合比」。

**审批状态**：作为 D-4 事故的根因修复一并实施，已随该提交生效。

### D-6　补充：`recalled` 从 `toolHistory` 重建会随会话历史膨胀（M1 验收发现）

涉及正文：§1.5「本会话历史召回由 `Session.toolHistory()` 重建」、§11 验收项 11。

**事实**：`toolHistory().updates[].additions` 记录的是「基线之后工具集新增了哪些」，
**不区分新增的原因**。召回归来、插件启停、配置放宽、MCP 连接建立，在它眼里完全一样。

**后果**：一个长期存在的会话反复经历工具集变化后，`recalled` 会逐渐涨到接近全集，
于是 `allow` 等于 `present`，限制形同虚设。方向是 fail-open（能力变多），
不会让会话失去工具，但 M1 的核心效果在旧会话上消失了。

**诊断数据**（`/snapshot` 的 `diagnostics` 字段）：

| agent | present | allow | 说明 |
|---|---|---|---|
| 新建的子会话 | 4 | 2 | 正确：只剩两个元能力 |
| 本会话（经历 3 次插件启停） | 36 | 36 | 限制生效，但名单等于全集 |

**结论**：M1 对**新会话**的行为正确，验收项 1–2 达标；对**长期会话**效果会退化。

**建议的修法（M2 实施，需另行审批正文）**：把召回集合自己持久化到
`<state>/recalled/<sessionId>.json`，读的时候优先用它、缺失时才回退到
`toolHistory` 重建。这样既满足验收项 11（重启后召回仍然有效），又不含历史噪音。

**同时新增**：`SnapshotResponse.diagnostics`（可选字段）暴露每个已绑定 agent 的
`presentCount / allowCount / restricted`。排查「插件已启用但某个会话没被收紧」时，
这是唯一能区分「没绑定」「绑定了但名单本来就有这么大」的地方。可选字段，不影响既有调用方。

### D-7　变更：Skill 目录走 pre-step 消息，systemPrompt 索引只列工具（M2 实施，已确认）

涉及正文：§3.4 的「索引注入」、§6.1 的 `skill-consumer/catalog-inject.ts`、§6.4、§6.6。

**正文现状与分歧**

- §6.6 把 Skill 索引并入 systemPrompt section；
- §6.1 与 M2 交付项又要求 `skill-consumer/catalog-inject.ts`（自建目录 + digest 增量替换）；
- 两者都实现会让同一份 Skill 列表在上下文出现两次。

**事实依据**

- `ctx.skills.snapshot()` 返回 Promise，而 `systemPrompt.section.text` 是同步回调，
  因此 section 无法在不预取、不缓存的前提下现查 Skill 注册表；
- 官方 `@deepseek-ai/dsh-tool-skill` 同样用 `agent/pre-step` 的 durable user message
  交付 `<available_skills>`，并以 digest 比较条目。

**处理结论（需求方确认）**

1. Skill 目录由 `skill-consumer/catalog-inject.ts` 在 `agent/pre-step` 注入 durable
   user message；条目变化时整表替换，不注入时发布空目录退役旧名称。来源 kind 用
   `capability-manager/skill-catalog`，与官方 `skill-catalog` 分开。
2. systemPrompt 索引 section 只列工具；Skill 名称由目录承担。
3. 注入条件按会话判定（不是只看全局配置）：

   | `meta_search` 可用 | 语义检索 | 目录 | Skill 召回通道 |
   |---|---|---|---|
   | 是 | 开启（模式 B） | 不注入 | 仅 keywords（语义） |
   | 是 | 关闭（模式 A） | 注入全部池内 Skill | 不召回；目录已全量，`names` 命中 Skill 时返回说明 |
   | 否（池外/黑名单/非常驻未召回） | 任意 | 注入全部池内 Skill | `meta_search` 不可调，不适用 |

4. `meta_search` 的 `names` 通道只召回工具；Skill 只经 `keywords` 的语义通道召回。
   这是需求方确认的口径：精确名称通道与「目录已全量」/「语义召回 Skill」两种模式
   互斥，不能让 names 绕过模式差异。
5. `skill` 工具本身不可用（池外/黑名单/非常驻未召回）时发布空目录，所有 Skill 都
   无法加载，与 §3.5 的提示一致。
6. 目录 listener 以 `{ prepend: true }` 注册在最外层。waterfall 的外层监听器在
   `next()` 返回后才追加消息，也就是最后写入 `decision.messages`；官方 consumer
   若在我们内层追加了空目录退役旧名称，我们的目录必须排在它后面才能生效。
   插件热启用、官方目录已经发布过时，首版目录用「替换」框架覆盖官方的退役声明。
7. 官方 consumer 的 `/name` 手势监听器不经过 shadow `skill` 工具，由用户显式发起
   时属于**最高优先级**：本插件不拦截、不做池/黑名单过滤，直接使用该 Skill。
   能力池、常驻与黑名单只约束模型自主调用、目录与召回；显式使用不受影响。
   （早期实现曾尝试过滤池外 Skill 的手势注入，已按需求方 2026-11-18 的明确口径撤销，
   见 D-11。）

**影响范围**：目录内容、去重载荷与界面摘要共用同一份 `describeSkill` 归一结果，
不会再出现「界面一份、索引一份、召回一份」的三种写法。§6.6 的「Skill 索引列全部
池内项」在语义上仍然成立，只是交付通道从 section 改为 pre-step 目录。

**审批状态**：**已确认（2026-11-18）**。正文未改动，本记录作为 §6.1/§6.6 的补充。

### D-8　变更：shadow `skill` 的 `when` 必须包含常驻/召回判定（M2 实施，已批准）

涉及正文：§6.4 的 `when: () => isInPool(...) && !isBlacklisted(...)`。

### D-9　补充：同一 agent 重复初始化必须先释放旧 restriction（M2 测试发现）

涉及正文：§6.3.2 `onAgentCreated`、D-3「重复调用是幂等的」。

**事实**：`onAgentCreated` 原先直接以 agent id 覆盖 binding，但没有先释放旧 binding
的 restriction。宿主重放 `agent/created`（或 D-3 的补一次与真实事件同时发生）时，
新 binding 的 `absorb()` 会在**旧 restriction 仍生效**的可见集上进行，`present`
只剩下上一次的可见集；被掩掉的工具从此再也回不来——与 D-4/D-5 的「会话锁死」
同一方向。

**处理**：`onAgentCreated` 在创建新 binding 前先对旧 binding 执行兜底释放器并
`release()`；这样吸收读到的是未受本插件限制的完整集合。`onAgentDisposed` 的
释放路径不变。

**影响范围**：只让「重复初始化」真正幂等，不改变首次创建的可见结果。集成测试
`tests/integration/host-wiring.test.ts` 与 `tests/host/enforcement/registry.test.ts`
覆盖该场景。

### D-11　补充：M3 的自建能力契约、默认值与置顶行为

涉及正文：§3.8、§3.10、§6.7、§6.8、§7.3、附录 B。

正文 §6.7 只给出「meta.json + impl.mjs」这一种自建工具形态，附录 B 又要求支持
声明式工具，而验收标准是「用 Skill 造一个声明式工具」。正文没有写错，只是没写全，
本节补齐 M3 落地时的契约与默认值。

#### 1. 自建工具的 `meta.json`

目录：`<state>/tools/<name>/meta.json`；目录名必须等于 `name`。

| 字段 | 必填 | 说明 |
|---|---|---|
| `name` | 是 | 小写 kebab 或 snake，≤64 字符，必须等于目录名 |
| `description` | 是 | 非空，工具摘要取首行 |
| `parameters` | 是 | JSON Schema，根节点必须是 `type: "object"` |
| `output` | 否 | `{ "schema": {...} }`，缺省 `{ "type": "object" }` |
| `kind` | 否 | `code` / `shell` / `http`；缺省时同目录存在 `impl.mjs` 即为 `code` |
| `shell` | kind=shell | `{ command, args?, timeoutMs? }` |
| `http` | kind=http | `{ url, method?, headers?, timeoutMs? }` |

- schema 只接受官方工具子集（`type`、`oneOf`、`properties`、`required`、
  `additionalProperties`、`items`、`enum`、`const`、`description`、`title`、
  `default`、`examples`），由 `@deepseek-ai/dsh-tools` 的断言收窄，失败信息带字段路径。
- `shell` 以 argv 数组执行，不经过 shell 字符串；`{{参数名}}` 在 argv、URL、
  请求头中展开，URL 位置做百分号编码，参数缺失展开为空串。
- `shell` 返回 `{ exitCode, stdout, stderr }`，非零退出码是结果而非异常；
  `http` 返回 `{ status, body }`，4xx/5xx 不抛错。
- 超时默认 30000ms，上限 600000ms；启动失败、超时、取消才抛错。
- `impl.mjs` 只认默认导出函数，结果必须是 JSON 值；每次调用按文件 mtime+size
  换模块 URL，因此改写后立即生效。高危模块导入只记 warning，不阻断注册。
- 名称含 `__` 的形式（MCP 风格）不被接受：那是 MCP 工具的命名空间，不是自建名。

#### 2. 发现与热更新

`<state>/tools` 与 `<state>/skills` 在插件启动时创建；工具按「名称 + 内容签名」增量
对账，内容变化先注销再注册，重复扫描不产生多余 `tools/change`。`fs.watch` 提供即时性，
每次读快照前再同步扫描一次作为兜底（监听失败时界面仍能自愈）。

#### 3. 内置 `capability-creator`

随包发布在 `skills/capability-creator/`，通过 `ctx.skills.register()` 注册；正文里的
`{{STATE_DIR}}` 在注册时替换为真实状态目录。目录缺失时只记 warning，不阻断插件加载。
说明文档按能力类型分四份：`tool-declarative.md`、`tool-code.md`、`skill.md`、`mcp.md`
（工具的两个形态各一份，正文附录 B 的「三支」指能力类型，不是文件数）。

#### 4. 手动创建 Skill

- 端点：`POST /capability-manager/api/skills`，请求 `{ revision }`；与配置写入共用
  `revision` 乐观并发。创建成功即把 `skill:<name>` 加入 `excluded`（新建默认在排出池，
  默认不常驻）。
- 默认基名 `my-skill`，冲突时依次 `my-skill-2`、`my-skill-3`…；默认描述
  「自建 Skill，用途待填写」。
- 骨架 = `SKILL.md`（frontmatter + 填写指引）+ `references/README.md`。
- 配置落盘失败时删掉刚建的目录并返回 `create-failed`，不留下「目录存在但不认识」的半截状态。
- 打开目录：`POST /capability-manager/api/reveal`，请求 `{ id }`；只接受自建能力
  （工具用 `<state>/tools/<name>`，Skill 用 provider 给出的包目录，不按名字拼路径）。
  平台命令 win32 = `explorer.exe`、darwin = `open`、其余 = `xdg-open`，子进程
  detach + unref。非自建能力返回 `not-owned`。

- `manual create` 成功后跳转 Skill 页、清空来源筛选与搜索词；

- `owned` 行在加号/减号左侧出现「打开目录」按钮，两侧都显示；

### D-12　补充：M4 角色黑名单的契约、优先级与刷新时机（M4 实施，无需审批）

涉及正文：§2.6、§3.6、§4.4、§6.1、§7.4、§11 验收项 1–2、§12。

M4 的交付是「`ctx.paRoles` 探测 + 手动绑定 + Router / Worker 配置区 + 黑名单应用与界面标记」。
正文没有写全的地方按本节执行，正文语义不变。

#### 1. 手动绑定的优先级（需求方 2026-11-18 确认）

角色判定顺序固定为：`ctx.paRoles` 有答案 → 用它；它返回 `undefined`（服务缺席、账本未就绪、
会话不属于 PA 域、抛错）→ 用 `roleBindings`；两者都没有 → 未知角色，不应用任何黑名单。

手动绑定是**补足**而不是覆盖：PA 的工单绑定是权威事实，两处都能回答时会话归属由 PA 决定。
`SnapshotResponse.sessions[].roleSource`（`pa` / `binding` / `unknown`）把来源暴露给界面，
用户因此能看出某条绑定是否真的在生效；PA 已判定而绑定仍存在时，界面标注「绑定休眠」。

#### 2. 契约扩展（只新增，未改既有字段语义）

- `ConfigPatch` 新增 `{ op: 'set-role-binding'; sessionId: string; role: SessionRoleName | null }`，
  `role: null` 表示解除绑定。`sessionId` 必须非空，且不能是会改写原型的键
  （与配置自愈用同一条判定），否则返回 `bad-request`。
- `SnapshotResponse.sessions?: SessionRoleSnapshot[]`：活跃会话的角色与来源；未知角色
  不带 `role` 字段；读不到活跃会话时整个字段缺省（而不是给空数组）。
- `SnapshotWarning.roles?: SessionRoleName[]`：黑名单类提示带上角色。两个角色各命中时
  是两条独立提示，所以角色是提示自身的属性，而不是挂在能力上的。

#### 3. 界面（需求方 2026-11-18 决定）

- 设置页改为「左侧分区导航 + 右侧内容」：设置分区会持续增加，导航必须独立于内容滚动。
- 角色相关分区（角色黑名单、会话角色）**只在检测到 `ctx.paRoles` 时出现**，严格对应
  §3.6 BL-7 与 §11 验收项 1；未检测到时给出说明，不摆一个能配置却不生效的面板。
- 角色黑名单：Router / Worker 两个并排面板，各自一份「已禁用置顶、组内名称序」的可搜索
  列表，行内开关表示「对该角色禁用」，另有清空入口（`clear-blacklist`）。池外能力照常
  列出并标注「池外」：黑名单与池互相独立，先配置、后入池是合法用法。
- 会话角色：每个活跃会话显示生效角色与来源；手动绑定用「自动 / 路由 / 执行」三态，
  「自动」即不写绑定，交回 PA 判定。
- **界面标记只在设置页**（需求方决定）：工具 / Skill 穿梭框的行内不加角色标签，
  避免同一行同时承载池、常驻与两个角色的状态。

#### 4. 刷新时机（已知限制）

黑名单在生成 `restrict` 名单时才求值，触发点是配置写入、`tools/change` 与召回后的重建。
PA 在会话进行中改变某会话的角色（账本新增工单）不会单独触发重建，该会话要等下一次配置
写入或工具变化才按新角色收紧；手动绑定走配置写入，因此立即触发重建。收紧方向对进行中
的会话仍受 `addition-only` 约束（§12），界面沿用既有提示。

### D-13　补充：M5 向量检索的实测结论、契约与实现口径（M5 实施，无需审批）

#### 1. 运行时选型实测（§12「向量运行时选型未实测」的结项）

| 项 | 结论 |
|---|---|
| 选定 | `onnxruntime-node@1.31.1`（方案首选：CPU、性能最好） |
| Electron 主进程 | **可用**。Electron 44.7.0 / Node 24.21.0 / N-API 10，`require('onnxruntime-node')` 与 `InferenceSession.create` 均成功 |
| 系统 Node | 可用（Node 24.17） |
| 会话创建 | 约 178 ms（24 MB int8 量化模型） |
| 单条推理 | 2–4 ms（5 token 输入，CPU，2 线程） |
| 输出 | `last_hidden_state` = `[1, seq, 512]`，CLS 池化 + L2 归一化后自相似度 1.0000 |

#### 3. 契约与开关语义

- `POST /embedding/enable` **同步等待**下载、校验与加载完成（需求方确认：没有百分比，转圈即可）：
  成功 `200 { ok: true }`；模型下载失败 `502` + `embedding-download-failed`；
  原生运行时无法加载 `503` + `embedding-unavailable`。失败一律**保持关闭**。
- `POST /embedding/disable` 恒 `200 { ok: true }`：关闭是能收敛到「关着」的操作。
- `SnapshotResponse.embedding.status` 仍是 `idle | downloading | verifying | ready | failed`；
  `progress` 不再使用（同步等待不需要实时进度）。
- 模式判定维持 §3.4：只看 `config.embedding.enabled`。为了让这个字段可信，服务在
  **启动时自愈**：`enabled=true` 但模型文件缺失、或加载失败，都会写回 `enabled=false`
  并记日志。否则「配置开着、索引不注入、keywords 又不可用」会让 mode B 空转。

#### 4. 检索接线

- 语义通道只在 `keywords` 非空且模式 B 时计算；候选 = 当前可召回集合
  （工具：池 ∩ 可见集 − 黑名单；Skill：池 − 黑名单），摘要规则复用 §4.2 的
  `summarize`（工具 description 首行截断 200、Skill 目录描述）。
- 返回 top-K 10、阈值 0.35；分数相同按能力 id 排序，保证同一批候选顺序稳定可复现。
- 向量缓存 `<modelDir>/vectors.json`：键为能力 id，命中条件是摘要的 sha256 一致；
  惰性读盘、原子落盘、坏数据退化为空表。推理失败只降级为 `notes` 里的说明，
  不让 `meta_search` 报错。
- 存储布局：`<state>/models/bge-small-zh-v1.5/{model_quantized.onnx,tokenizer.json,config.json,manifest.json,vectors.json}`。
- 测试/无原生运行时环境可通过 `apply(ctx, { embedding })` 注入假下载器与假嵌入器；
  生产不传，行为不变。

#### 5. 已知限制

- 首次开启的 HTTP 请求会挂到下载 + 加载结束（本机约 45 s），期间界面保持 saving；
  下载器单请求超时 120 s，慢网会以 `embedding-download-failed` 收场而不是无限等待。
- `onnxruntime-node` 解压约 307 MB，是目前最重的依赖；换 WASM 可减半但推理慢一个量级，
  按方案与实测选择保留 node。
- 启动自愈只比对模型文件**大小**；大小一致但内容损坏的情况由「加载失败 → 自愈关闭」兜住。
- 新增或修改能力导致摘要变化时，该条向量会在下一次检索时重算（只重算变化的那条）。
