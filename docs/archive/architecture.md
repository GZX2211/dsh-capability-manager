本文档说明本项目的核心架构、设计意图与关键取舍。

---

## 1. 问题与定位

模型可见的工具集随插件增长而膨胀：每个工具的完整 schema 都占用上下文与 KV 前缀，工具越多，模型的选择面越宽、判断成本越高。与此同时，“哪些能力可用、哪些启动即见、哪些按需召回”分散在官方工具、自建工具、MCP 连接、Skill 目录等多套机制里，用户缺少一个统一的治理面，也难以让角色差异与全局配置共存。

`dsh-capability-manager` 构建在 DeepSeek Harness 之上，把能力供给从“静态全量”改为“可治理的按需面”：以能力池作为硬白名单，以常驻作为启动可见集，以 `meta_search` 作为按需召回通道，并在检测到 dsh-personal-agent 插件（同作者的另一个插件）时叠加角色黑名单。它不重建任何运行时能力，只通过 Harness 的公开接口收放可见性。

项目的核心不是在“全量暴露”与“完全隐藏”之间选择一种模式，而是让能力的可用范围、启动可见性与召回时机能够按需分配，并且在配置变更后热生效、可观察、可回退。

## 2. 核心架构

整体分层如下：

```text
┌─────────────────────────────────────┐
│                Client               │
│   能力池 / 常驻 / 黑名单 / MCP 治理   │
└──────────────────┬──────────────────┘
                   │ HTTP API
┌──────────────────▼──────────────────┐
│                 Host                │
│                                     │
│  判定链：黑名单 > 池 > 常驻 > 召回    │
│  执行面：restrict / 目录 / 索引 / 召回 │
│  配置面：自愈、原子写、同源写路径      │
└──────────────────┬──────────────────┘
                   │ Harness 公开能力
┌──────────────────▼──────────────────┐
│           DeepSeek Harness          │
│   Tools / Skills / Session / MCP    │
└─────────────────────────────────────┘
```

### 2.1 单一的判定链

“某能力对某 Agent 是否可用”只有一条判定链：角色黑名单 → 能力池 → 常驻 → 召回 → 使用，先命中先决定。所有执行面——`restrict` 名单、Skill 目录、`meta_search` 候选、索引注入——都是这条链的投影，不允许各自实现口径。

判定链集中，意味着任何“可见性”问题都能回到一处解释；代价是每新增一个执行面，都必须确认它没有绕开判定链。

### 2.2 供需面与执行面分离

配置（池、常驻、黑名单、角色绑定）是声明式的供需面；`restrict` 名单、目录注入、索引注入、召回结果是执行面。执行面从配置派生，不反向写配置。

这使配置可以自由演进、自愈、跨会话重建，而执行面能在 Agent 生命周期内反复重建而不污染真源；也让“配置正确但执行未生效”成为可单独诊断的一类问题。

### 2.3 召回是显式的增量供给

模型启动时只看到常驻能力，其余能力经 `meta_search` 召回后进入会话历史，成为后续 step 的可见集。召回载荷自带完整 schema，使模型凭返回值即可调用；同一 step 内的召回要等下一步才可执行，这是增量供给的固有延迟，而非缺陷。

供给面因此被拆成“启动即见”与“按需出现”两段，新增能力不会冲击已有的 KV 前缀缓存。

### 2.4 配置同源，不持有副本

MCP 配置的读走官方 `mcp-manager`，写走官方 `config-editor`，与 Agent 和官方 Settings 是同一份；自建工具与 Skill 的真源是状态目录，插件通过监听发现并注册，而不是另建索引。插件是治理面，不是第二份真源。

同源的收益是列表、状态与外部编辑天然一致；代价是依赖官方写路径与 Loader 对账可用，不可用时只能降级为只读并说明原因。

## 3. 关键设计取舍

| 设计选择 | 主要收益 | 需要承担的代价 |
| --- | --- | --- |
| 能力池硬白名单 + 常驻子集，而非全量暴露 | 上下文成本可控，模型选择面收敛 | 需维护索引与召回通道，用户需理解两层状态 |
| `meta_search` 按需召回，而非静态注入全部 schema | 新增能力不破坏 KV 前缀缓存 | 召回有一步延迟，同 step 内不可立即调用 |
| 黑名单 > 池 > 常驻的严格优先级 | 角色差异可表达且不与全局配置冲突 | 黑名单可排除常驻，需界面提示与测试覆盖 |
| 执行面全部从判定链派生，不各自实现 | 口径统一，可单测，可审计 | 任一执行面新增都要回到判定链确认 |
| MCP 配置同源官方写路径，不自持副本 | 与 Agent / Settings 天然一致 | 依赖 Loader 条目与 editor 可用，否则只读降级 |
| shadow `skill` 工具接管 Skill 供给 | Skill 与工具受同一套池与黑名单管辖 | 需与官方目录注入协同，避免重复注入 |
| 收紧配置对进行中会话延迟可见 | 不破坏 addition-only 与 KV 缓存 | 界面必须提示，必要时新建会话 |
| 用户 `/name` 手势不受池限制 | 显式使用优先，人在回路不被治理面阻断 | 与“池外不注入上下文”需在文案上区分清楚 |

这些取舍并不意味本项目拥有更优的能力治理方式。它追求的是一种可配置的供给架构：根据上下文预算、任务不确定性与治理要求，在“预置可见”与“按需召回”之间选择合适的平衡。

## 4. 架构不变量

以下约束构成长期架构边界：

1. **Harness 优先。** 工具、Skill、Session、MCP 连接由 DeepSeek Harness 提供，插件只通过公开能力扩展，不在插件内重建或修改运行时。
2. **单一判定链。** 黑名单 > 池 > 常驻 > 召回 > 使用，任何执行面不得偏离这条链，也不得引入第二套可用性口径。
3. **供需面与执行面分离。** 执行面从配置派生，不反向写配置；配置是真源，执行是投影。
4. **配置同源。** MCP 与自建能力的真源在官方 manager 与状态目录，插件不持有第二份副本，也不自写 patch 绕过对账。
5. **失败朝不生效降级。** 吸收失败、候选为空、名单为空时一律不收紧；绝不出现“工具被收走、召回又不可用”的组合——本插件的限制会收走使用者自己的工具，降级方向必须是可用而非全盲。
6. **收紧延迟可见。** 在 addition-only 下移除不发通知，界面必须如实提示延迟，不以“已生效”掩盖进行中会话的旧视图。
7. **显式使用优先。** 能力池、常驻与黑名单约束模型自主调用与能力供给面；用户显式点名使用不受此约束。

以上约束用于界定架构边界与评估设计变更。具体实现以代码和测试为准；当长期架构原则发生变化时，应同步更新本文档。
