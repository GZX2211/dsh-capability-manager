### 1.1 探针实测结论（2026-11-17）

用一个临时探针 bundle，在 `agent/created` 内对第一个新 agent 依次应用 restriction，实测结果：

| 阶段 | 可见工具数 | 结果 |
|---|---|---|
| 初始 | 41 | 含 `pwsh/read/write/edit/glob/grep/skill/subagent/workflow/office_*/schedule_*/team_task_*` |
| `restrict({ allow: ['read','grep'] })` | **2** | 只剩 `read,grep` |
| `dispose()` | 41 | 完全恢复 |
| `restrict({ allow: ['read','grep','glob'] })` | 3 | `glob,grep,read` |

**结论**

- ✅ `restrict` 在 `agent/created` 内**同步生效**（不需要等下一个 turn）
- ✅ 能掩掉 **standard preset 挂载的全部工具**——preset generation scope 是 agent scope 的父层，`view()` 的 `own` 只豁免 agent 自己那一层
- ✅ dispose 后完全恢复，重建 restriction 立刻生效（动态白名单可行）
- ✅ `tools/change` 事件确实发出

> **事故记录（必须成为开发规则）**：同一探针在 `agent/pre-step` 上注册了普通监听器并返回 `undefined`，
> 导致整个 Host 崩溃（`Cannot read properties of undefined (reading 'kind')`）。
> 该事件是 **waterfall**：签名 `(payload, next) => Promise<PreStepDecision>`，
> 返回值必须是 `{ kind: 'reject' }` 或 `{ kind: 'enter', messages, startsRequestSeries? }`。
> **规则：waterfall 事件一律用 `ctx.waterfall(...)` 注册并返回 `next()` 的结果；普通监听器只用于 event 模式。**

## 2. 核心机制（已验证）

### 2.1 硬白名单 = `restrict`

`dsh-tools/src/index.ts:162-189`

```
restrict(filter) → disposer
  必须 agent.ctx 调用（全局调用直接抛错）
  allow = 只留这些；deny = 去掉这些；多条取交集
  作用域：global 层 + 祖先 scope 层
  不起作用：当前 scope 自己注册的工具（own 层豁免）
  名单含未知工具名 → 抛错
```

`dsh-personal-agent/src/host/sessions/decorate.ts` 已在生产路径使用，并写了 `restrictableNames()` 先过滤未知名字。

### 2.2 工具集变化是原生增量协议

`dsh-agent-loop/src/agent.ts:698-710`：每请求前 diff `request/header.tools`，产生 `developer/message`
含 `tool-addition` / `tool-removal`。`dsh-session/src/tool-history.ts` 折叠成 `ToolHistory`。

profile 已配 `toolUpdate: addition-only`、`systemPromptUpdate: in-history`：

- 新增工具 → 不破坏 KV 前缀 ✅
- 移除工具 → **不发移除通知**（模型会以为还能用）⚠️

### 2.3 条件注册 = `when`（只对自己的注册有效）

`register(def, { when })` 每 step 求值。官方范例 `dsh-tool-office` 就是「标记激活后才出现」。
对官方工具无法加 `when`，只能用 `restrict`。

### 2.4 上下文载荷的权威读取点

- 工具完整 schema：`Session.toolHistory()`
- Skill 索引：会话日志中最新 `skill-catalog` 消息

## 3. 三个关键问题的深度结论

### 3.1 Skill 侧：为什么「只管自建 Skill」不成立

**你的设想是**：官方 Skill 该注入就注入，自建 Skill 走召回。

**技术上不成立**，原因是官方 `dsh-tool-skill` 的 catalog 是 **all-or-nothing**：

```
dsh-tool-skill/src/index.ts:226-229
  snapshot = await ctx.skills.snapshot({ cwd, signal, scope: agent })
  skills   = snapshot.skills.filter(isModelInvocable)     // 全量，无过滤钩子
```

自建 Skill 只有两个位置：

| 注册方式 | 进官方 catalog？ | 官方 `skill` 工具能加载？ |
|---|---|---|
| `modelInvocable: true`（默认） | ✅ 进（**无法排除**） | ✅ 能 |
| `modelInvocable: false` | ❌ 不进 | ❌ **不能**（`index.ts:142,149` 拒绝） |

所以「自建 Skill 不进 catalog 但能加载」这个组合**不存在**。要它成立，必须自建第二个加载工具——
那已经是半个 consumer，却只覆盖自建 Skill，还制造两套 Skill 语义（模型要记住哪个用 `skill`、
哪个用 `capability_load`），比直接全量接管更糟。

#### 三个方案的诚实对比

| | S-A 复用官方 | S-B 全量 shadow | S-C 只管自建 Skill |
|---|---|---|---|
| Skill 能进能力池 | ❌ | ✅ | ❌（官方那部分仍不可控） |
| Skill 能进角色黑名单 | ❌ | ✅ | ❌ |
| 模式 B「Skill 索引不常驻」 | ❌ | ✅ | ❌ |
| 非初始 Skill 走召回 | ❌ | ✅ | ⚠️ 仅自建部分 |
| 官方 catalog 收益（digest 增量、incomplete 降级、`/name` 手势） | ✅ 白拿 | ⚠️ 部分需重写 | ⚠️ 分裂 |
| 代码量 | 0 | ~250 行 + 测试 | ~200 行（且语义更乱） |
| 与官方版本漂移风险 | 无 | 中（但可复用导出） | 中 |
| 需求文档改动量 | **大**（Skill 章节几乎全删） | 小 | 中 |

**推荐 S-B（全量 shadow）**，理由：

1. 它是唯一能让 Skill 真正进入「能力池 / 角色黑名单」这个核心语义的方案。
2. 工作量被低估了——官方把可复用的东西都导出了：
   `dsh-skill` 导出 `renderSkillContent()`、`isModelInvocable()`、`isUserInvocable()`。
   我们只需要接管**筛选**与**注入时机**，渲染仍走官方函数。
3. shadow 机制是官方文档明确支持的：`dsh-tool-skill/README.md:85`
   > a scoped same-name shadow removes both the schema and its guidance
4. shadow 后官方 catalog 不再注入，不会出现「两份索引」。

#### S-B 的实际实现面

| 组件 | 做法 | 估算 |
|---|---|---|
| shadow `skill` 工具 | agent.ctx 注册同名 definition：`get()` → 校验池 → `renderSkillContent()` | ~80 行 |
| 自建 catalog 注入 | `agent/pre-step`：`snapshot` → 过滤 `isModelInvocable` → **过滤池** → 渲染 → digest 比对 → 注入 | ~120 行 |
| 池过滤 | shared 层纯函数（`capability ∈ pool && ∉ roleBlacklist`） | ~40 行 |
| `/name` 手势 | 官方监听器在 shadow 后**仍然运行**，会注入正文且不受池管控 | 可选：拦截或接受 |

**一个额外收益**：自建 catalog 后，「模式 A 常驻哪些 Skill 索引」变成我们自己的设计自由度（见优化建议 O6）。

**一个额外代价**：官方升级若改了 catalog 形状或 `renderSkillContent` 签名，需要跟进。

### 3.2 向量检索：实测结论

#### 模型源（三源均可达，本机实测 HTTP 200）

| 源 | 内容 | 备注 |
|---|---|---|
| `huggingface.co` | ✅ 200 | 直连 |
| `hf-mirror.com` | ✅ 200 | 国内镜像 |
| `Xenova/bge-small-zh-v1.5` | `onnx/model_quantized.onnx` **24.0 MB** | 单文件，最易下载校验 |
| | `onnx/model.onnx` 94.8 MB（fp32） | |
| | `tokenizer.json` 439 KB、`config.json` 716 B | |
| `onnx-community/bge-small-zh-v1.5-ONNX` | 外部数据文件格式（`.onnx` + `.onnx_data`） | 需两文件同目录 |

**选定**：`Xenova/bge-small-zh-v1.5` 的 `onnx/model_quantized.onnx`（int8, 24 MB）+ `tokenizer.json`。
单文件、体积小、与 SenseVoice 的下载+sha256 校验模式一致，可直接抄它的多源探测逻辑。

#### 运行时三选一（需实测后定）

| | 依赖 | 体积 | 性能 | 风险 |
|---|---|---|---|---|
| E1 `@huggingface/transformers` | 含 onnxruntime 原生 | 重 | 快 | 原生二进制、跨平台、版本耦合 |
| E2 `onnxruntime-node` + 自实现 WordPiece | 原生 | 中 | 快 | 要自己写 tokenizer（~150 行） |
| E3 `onnxruntime-web`（WASM） | 纯 JS+wasm | 轻 | 慢 2–4× | **需实测 Electron 主进程能否跑 WASM backend** |

**倾向 E3 或 E2**：插件要装进 profile，原生二进制会带来跨平台安装问题；
工具+Skill 总量只有几十条，WASM 慢几倍也完全够（单次检索几十毫秒级）。

#### 必须自建的（官方无对应能力）

1. 模型下载 + sha256 校验 + 多源回退（照抄 SenseVoice 的 `runtime/assets.json` 模式）
2. 向量缓存（能力条目变化时增量重算）
3. 余弦相似度 top-K

### 3.3 角色判定：契约设计

PA 当前把判定逻辑放在 `src/host/sessions/decorate.ts:roleForSession()` 内部，
依赖账本 kv 与投影，**未导出任何 Cordis service**。

既然 PA 可改，设计为**契约先行、分级降级**：

```ts
// 能力管理暴露的注册点（PA 后续调用；能力管理不 import PA）
ctx.capabilityManager.registerRoleResolver(
  (session) => 'router' | 'worker' | undefined
)

// 判定优先级（先命中先决定）
1. 已注册的 resolver（PA 提供）
2. 内置降级：session/workspace 标题启发式
3. 用户手动绑定（管理界面覆盖）
```

**为什么这样设计**：

- 保持需求的「单向感知」：能力管理主动探测 PA，PA 不感知能力管理的存在（它只是调用了一个它知道的接口）。
- PA 改造前功能可用（降级 2/3），改造后自动升级，不需要两边同时上线。
- resolver 是纯函数（`Session → 角色`），符合仓库「确定性计算必须纯函数」的规范。

PA 侧后续只需在 `decorate.ts` 装配处加一行注册，`roleForSession()` 本身不用改。

## 4. 仍需修正的需求点

### C2　能力池管辖不到「agent 自身 scope」注册的工具

实测确认 scope 链是（nearest-first）：

```
agent scope              ← createScope(loopCtx, agent)；agent.ctx 注册的东西在这一层
  ↑ parent
preset generation scope  ← standard preset 的 41 个工具在这一层
  ↑ parent
root / global            ← dsh-base 的全局工具
```

`restrict` 作用于**除 agent 自己那一层以外的所有层**，所以：

- ✅ preset 挂的工具（41 个里的绝大多数）—— 可掩
- ✅ global 层工具 —— 可掩
- ❌ 通过 `agent.ctx.tools.register()` 注册在 agent 自身 scope 的工具 —— **不可掩**

当前落在 ❌ 里的只有 PA 的 3 个领域工具：

| 角色 | 工具 |
|---|---|
| Router | `pa_task_route`、`pa_ledger_query` |
| Worker | `pa_approval_submit` |

（另外：subagent 若通过 `agentOptions.setup(agentCtx)` 注册工具，也属这类；当前官方未使用该注册方式。）

**建议**：能力池定义为「**注册在 agent 之上**的工具」（global + preset），
管理界面对 agent 专属工具单列一组「会话专属 · 不受管辖」，不需要改核心语义。

### C3　公式 4.3 与需求 23（重启后无需重新召回）矛盾

需求 4.3：`启动直接能力 = 初始配置 ∩ (能力池 − 黑名单)`。
需求 23：召回结果进会话日志，重启后仍在，不需要重新召回。

只按 4.3 算，重启后历史召回的工具有 `tool-addition` 记录在上下文、却不在 `allow` 里
→ 模型看到「可用」、调用报 `UNKNOWN_TOOL`。

**建议修正**：

```
某会话可用工具 = (初始配置 ∪ 本会话历史召回) ∩ (能力池 − 该角色黑名单)
本会话历史召回 = 折叠会话日志中的 tool-addition − tool-removal（= Session.toolHistory()）
```

### C4　`addition-only` 下「收紧配置」对进行中会话不可见

官方行为：移除工具不发送移除消息。用户把工具移出池/加入黑名单后，进行中的会话模型仍以为可用。

**建议**：接受并在管理界面提示「收紧配置对进行中会话有延迟，必要时新建会话」。
不要为让模型「知道工具没了」而改为全量重发（会毁掉前缀缓存）。

### C5　工具索引的「副作用」官方无数据源

`ToolDefinition` 只有 `isConcurrencySafe?(args)`，**没有副作用字段**。
需求 TI-1 的「副作用」必须自建：人工表 + 内置默认表（覆盖官方工具）+ 未知标 `unknown`，界面可编辑。

### C6　MCP 页与官方 Settings 重复

官方 `mcp-manager` + Settings 已提供完整的新建/配置/启停/凭据模板（`${credential:REF}`）+ revision 校验。
插件内再造编辑器会形成两个真源。

**建议**：MCP 页做只读视图 + 跳转官方设置，插件只承担「池内/池外」这一层。

### C7　模式 A 下 `meta_search` 的 Skill 通道返 0 会让模型反复重试

**建议**：去重剔除后，若本次是 Skill 通道且处于模式 A，返回值追加一行说明
「Skill 索引已在当前上下文全程可见，无需召回」。纯文案，不改契约。

## 5. 优化建议

### O1　三档集合简化为两档

需求有「能力池 / 初始配置 / 召回记录」三份集合，用户每加一个工具要想它在哪一层。
实现上 `restrict.allow` 本来就是 `常驻 ∪ 召回`，**「池」没有独立存在的位置**。

改为：**可见集**（可召回可用）+ **常驻集**（启动即在上文），召回记录是运行时派生，不进配置。

### O2　`meta_search` 分两段返回

```
{ tools: [{ name, schema }], skills: [{ name, description }], notes: [...] }
```

工具直接调用、Skill 再调 `skill`，消费方式完全不同，混在一个列表里模型容易对 Skill 也直接「调用」。

### O3　工具索引做成可选提示区块

`systemPrompt.section()` 会让 system prompt 变长，每次开关都破坏前缀缓存。
需求 7.3 已意识到「索引常驻只占上下文不产生召回能力」的浪费，说明这条边界本来就该由用户看见代价。

### O4　角色黑名单做成「角色模板 + 批量应用」

Router 典型排除写操作类、Worker 典型排除 UI 类。PA 自己就是这么做的
（`ROUTER_DENY` 7 个 / `WORKER_DENY` 3 个常量）。逐条勾选几十个工具在 UI 上不可用。

### O5　向量开关做「两段式」

默认关闭 → 点开启 → 先做模型可用性检测（路径/哈希/加载）→ 通过后才启用。
需求 SW-2 只说了「失败保持关闭」，没定义「什么时候算失败」。

### O6　自建 catalog 后，「模式 A 常驻什么」重新设计

S-B 拿下 catalog 控制权后，模式 A 不必照抄官方的「全量注入」：

- **方案 a（照抄官方）**：常驻池内全部 Skill 索引 → `meta_search` 的 Skill 通道恒返 0
- **方案 b（与工具侧对称）**：只常驻**初始 Skill** 的索引，非初始 Skill 走召回 → Skill 通道有效

方案 b 让「工具」和「Skill」两条链路的语义完全一致（初始常驻 / 非初始召回），
也顺手解掉 C7 那个「返 0 让模型困惑」的问题。代价是偏离需求 MA-2/MA-4 的原始描述。

### O7　工具索引与 Skill 索引合并为一个 section

两者都是「有什么、大概做什么」，合成一个 section 少一次 prompt 组装开销，模型也更容易对照。
（S-A 方案下不可行，S-B 下可行。）

## 6. 落地顺序

```
里程碑 1（无 embedding、无 shadow，纯工具白名单）
  配置持久化 + agent/created 应用 restrict + meta_search 正则召回
  + 工具索引 section + 管理界面（工具池 / 初始配置）
  → 目标：验证 restrict + tool-addition 这条核心假设

里程碑 2（Skill 侧）
  按 D-4 决议执行 S-B（shadow 自建 catalog + skill 工具）

里程碑 3（角色黑名单）
  resolver 契约 + 降级判定 + 两个窗口；PA 接口后补

里程碑 4（向量检索）
  模型下载/校验 + 运行时选型 + 模式 B

里程碑 5（MCP / 自建能力入口 / 版本控制）
```

**理由**：里程碑 1 不依赖模型、不依赖 PA、不依赖原生二进制，能最快证实或证伪核心假设。
