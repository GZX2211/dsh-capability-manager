感谢你愿意把时间和想法投入这个项目。这是一个研究驱动的个人项目，欢迎各种形式的贡献：bug 修复、文档改进、界面优化、召回与治理机制增强、新功能尝试，以及基于本架构的二次开发。

## 先了解项目边界

这个项目有明确的架构立场——可治理的按需能力供给。以下内容不建议直接提 PR 修改，有不同想法欢迎先开 Issue 讨论（完整表述见 [架构文档](architecture.md) 的「架构不变量」）：

- **Harness 优先**：工具、Skill、Session、MCP 连接由 DeepSeek Harness 提供，插件只通过公开能力扩展，不在插件内重建或修改运行时；
- **单一判定链**：黑名单 > 池 > 常驻 > 召回 > 使用，任何执行面不得偏离这条链，也不得引入第二套可用性口径；
- **供需面与执行面分离**：执行面从配置派生，不反向写配置；
- **配置同源**：MCP 与自建能力的真源在官方 manager 与状态目录，插件不持有第二份副本，也不自写 patch 绕过对账；
- **失败朝不生效降级**：绝不出现「工具被收走、召回又不可用」的组合——本插件的限制会收走使用者自己的工具，降级方向必须是可用而非全盲；
- **显式使用优先**：用户 `/名称` 手势不受能力池、常驻与黑名单约束。

**其余一切都开放**

## 提交 PR

PR 小而精最受欢迎。小型、聚焦的 PR 更容易快速处理。

大型重构或功能重写建议先开 Issue 聊一下。这类 PR 可能不会被直接合并，但我会认真阅读、评估，并把其中有用的部分提取出来，融入现有架构。

项目迭代较快，你基于 fork 时的代码提交即可，不必担心合并冲突。机械性冲突由我处理；如果涉及语义变化，我会在 PR 中和你确认。

## 扩展，而不是修改

如果你对架构有想法，最友好的参与方式是 **fork 这个仓库，基于它的架构做二次开发，或者创建你自己的 DSH 插件**。你不需要等待评审，实现可以立即服务于你自己的场景，也能持续同步上游的改进。

如果你在扩展过程中发现架构层面的不足，欢迎回来开 Issue 讨论。有真实实现支撑的反馈，远比抽象的设计有分量。

## 开发与测试

开发环境搭建、构建、测试与类型检查的命令见 [README](../README.md) 的「本地开发」一节。提交前请确保 `pnpm check`（类型检查 + 测试 + 构建）通过；新增了行为，请附带对应的测试。

几条本仓库的硬约定（完整规范见根目录与各子目录的 `AGENTS.md`）：

- **纯函数优先**：判定、归一化、投影等确定性计算必须是纯函数，数据传入即全部事实；共享层 `src/shared/` 禁止运行时 import。
- **测试镜像源码**：`tests/` 下的单元目录镜像 `src/` 结构，文件名为 `<source-name>.test.ts`；新增业务逻辑必须有测试覆盖，新增代码行覆盖率目标 ≥ 80%；禁止为让测试通过而删断言或放宽条件。
- **文案必须双语**：任何用户可见的界面文字走 `src/client/i18n.ts` 的 `zh` / `en` 词典同步新增，禁止组件内硬编码。
- **注释只写 why**：补充代码未表达的约束、决策背景与陷阱，不复述代码；行为变更同步更新或删除注释。
- **契约变更同步检查**：修改公共接口、数据结构或契约时，必须同步检查调用方与测试；行为变化显式记录，纯重构不得夹带行为变化。
