## 一、对象与术语（请先确认理解一致）

- **DSH（DeepSeek Harness）**：宿主桌面端 Agent 应用，本地已安装且当前正在运行。负责模型调用、工具调度、上下文与会话管理。
- **dsh-capability-manager**：我为 DSH 开发的能力管理插件，路径 `D:\AiCoding-Gzx\HarnessPlugin\dsh-capability-manager`。它的核心机制是**能力池的选择性加载**：控制哪些工具进入本次会话的上下文，以及 meta_search 能力。
- **prime-agent**：你本体的源码，路径 `D:\AiCoding-Gzx\prime-agent`。其中包含我想要的目标能力：**一个跨调用存活的持久 Python 内核**，以及围绕它的 `run_python`（你的工具不叫这个名字，这是我打算命名在插件内的名字） 工具定义与执行协议。

## 二、目标

把 prime-agent 中「持久 Python 内核 + run_python」这套能力移植/复刻到 dsh-capability-manager 中，使 DSH 经由该插件获得持久 Python 内核执行能力。

## 三、核心设计意图（请理解后再评估）

依托插件的选择性加载机制，同一套内核要支撑两种运行形态：

- **模式 A（纯内核）**：只加载 `run_python`，其余工具全部排除出能力池。模型上下文中仅有一个工具，所有能力都靠写 Python 代码完成，行为等价于 prime-agent 当前的执行体系。
- **模式 B（混合）**：`run_python` 与其他工具（文件、检索、todo_write等）同时加载。既有 ReAct 循环的多工具调用能力，又有内核的状态保持能力。

我的判断是：A、B 各有优劣，应当能在同一实现中共存、切换或组合，而不是只落地其中一种。
